# Application identity modes v0.21 — operator and compatibility contract

Select TENANT_AWARE for principal + tenant + role verification or PRINCIPAL_ROLE for an explicitly tenantless principal + role application. Both require genuine native principal/role matches, three distinct target-bound saved actors for guided mapping, explicit GET scope, immutable plan approval and separate proof review. Distinct roles are not distinct principals. Explicit principal/role field mappings must be different; mapping the identity field as role is refused.

In existing onboarding, choose the identity model before entering credentials. PRINCIPAL_ROLE omits tenant actor fields and tenant JSON paths; it does not generate replacements. Select the same model in guided mapping. Onboarding saves the mode in safe identity metadata, and mapping returns/binds it in actor plans. Editing the mode invalidates local approval; changing saved profile mode/secret invalidates server context digests. The server and native worker remain authoritative. Missing, conflicting, unverified or contradictory identities do not become proof.

Native principal-role results carry identityModel=PRINCIPAL_ROLE and tenantVerification=NOT_APPLICABLE. They omit tenantMatched and tenantHash. NOT_APPLICABLE is not successful tenant verification. Tenant-aware results must still match tenant metadata. Historical application inputs and reports without a model remain tenant-aware in guided evidence; their stored bytes/digests are not rewritten. Explicit mode is included in new plans, comparison fingerprints, context bindings, hypothesis identities and handoff. Older tenant-aware evidence cannot be replayed under principal-role mode.

Readiness reads records only: declared identities are not native-verified, and no credential decryption, target request or execution approval occurs. Opaque Bearer sessions remain encrypted and target/organization/expiry-bound. Profile disable/revocation and stale native source must be reviewed, never silently retried or cleared. Existing identity endpoint consent and all other operational holds remain unchanged.

Supported now: scalar object/function mapping, verified principal/role identity, source-grounded scalar hypotheses, explicit policy review, bounded native proof and handoff. Tenant-isolation contracts are refused for principal-role actor plans. Tenant-specific business transitions/relationship schemas and minimized owner-intake artifact formats still require their original tenant evidence; they remain conservatively unavailable for tenantless workflows. Collection ownership remains deferred under COLLECTION_OWNERSHIP_NEXT_STAGE_v0.22.md. No substitute tenant or first-entry array marker is acceptable.

The Decide pilot remains blocked for genuine profiles, isolated PostgreSQL/users bootstrap, controlled background jobs/listener/outbound services and explicit review of authenticated GET session timestamp writes. No Decide application/source/environment/database was changed, started or contacted in this increment. Tests use synthetic owned Windows applications only; successful code conformance is not real Decide acceptance or independent detection accuracy.
