# Reviewed state-transition observations v0.1

## What this increment proves

RouteCairn can correlate two immutable native application maps with a signed target event and a human-reviewed role/state policy. It can then run the existing bounded GET matrix against exact postconditions, retain role-read-boundary findings, and compare a separately approved remediation retest. It does not execute a transition, verify mutation authorization, or prove causation. A successful read-only matrix attached to a transition is INCONCLUSIVE overall: verifiedReadOnlyChecksPass may be true, while verifiedPass remains false. Actual role-access violations remain FINDINGS with their native controls. No state-changing dispatch or automatic replay was added.

Declare exact non-mutating GET routes with object, tenant, one business-state path and a distinct numeric revision path. The existing two-state-field limit remains; a transition needs a state field plus its revision. Acquire a before map through the existing separate native consent.
2. The owner performs the intended fixture/model change outside RouteCairn execution. Retain the target's event record and independently provision its trusted public-key SHA-256. Do not derive trust merely from a key included in the event. The two owned application fixtures sign a record, retain a separate public-key authority receipt before requests, and expose the record through an authenticated target HTTP GET.
3. Acquire an after map using the same target, routes, credentials and authority context. Open hypotheses, select two to four ordered routes, and draft the existing differential flow. Ordering and cross-step relationships are human declarations, not discovered causal edges.
4. Load the immutable before observation, import the public signed-event JSON, enter its independently trusted key hash, declare LEGITIMATE or FORBIDDEN and explain the purpose. Drafting makes zero target requests. Inspect exact source hashes, typed markers, actor/tenant identity, revisions, signature and missing controls. ABSTAIN cannot be overridden by checkboxes.
5. Confirm this exact key's event/revision authority and a meaningful purpose and consent for every route/actor GET. Complete the existing exact object/tenant/state and role ALLOW/DENY review, ownership confirmation and relationship rationale. A transition proposal requires whole-flow review; the individual-candidate review branch is refused. This records an immutable decision and ordinary Workbench matrix, without transmission.
6. Separately review the existing exact bounded proof plan and consent to native GET execution. Every state and revision is checked through the existing API module, positive controls and actor-specific prerequisites. Wrong resources, state drift, missing identity or prerequisites remain inconclusive. Existing scope, DNS, request/response, authorization, process-custody, cleanup and one-use dispatch guarantees remain.
7. Interpret the result by scope. Passing read-only checks do not establish a clean state-transition assessment. The result displays the recorded event, declared policy, state/revision pair, review/key/source bindings, and links to both existing scan detail views. A declared forbidden event requires human interpretation; a signature does not itself create a vulnerability finding.
8. For a role-read-boundary remediation, create a new version with the identical pinned review/policy/source inputs, separately approve its native GET proof, and compare retained executions. Two resolved role findings do not mean state-change authorization was verified. Changing policy requires a new proposal/review; supersession invalidates old-matrix admission. Missing matrix acknowledgment stays visible and is never automatically retried or adopted.

## Signed target-event format and trust

The public input file has exactly publicKeySpki, signature and event. Never upload a private key. The UI bounds it to 16 KiB; the server independently validates the strict flat typed contract and all bounded string/number fields. The reviewed declaration separately includes the before-map ID, policy, purpose and manually trusted key SHA-256.

event has exactly: eventId (UUID), targetOrigin, routeId, actorId (primary/account-a/account-b), principalId, actorTenantId, role, resourceValue, tenantValue, statePath, beforeState, afterState, revisionPath, fromRevision, toRevision and occurredAt (ISO datetime). Resource/tenant/state values are approved non-secret finite numbers or nonempty strings. Revisions are safe nonnegative/positive integers and must advance exactly once. State/revision paths must be distinct fields already present in the native mapping contract, separate from identity/tenant fields; existing secret/prototype-path refusal remains.

Signing bytes are UTF-8: the literal domain routecairn-target-transition-event-v1, one LF, then canonicalExecutablePlanJson(event). Canonical JSON recursively sorts object keys, rejects unsupported values and normalizes negative zero; array order is retained. The key is Ed25519 SPKI DER (44 bytes), base64 encoded; the signature is 64 bytes, base64 encoded. The trusted fingerprint is SHA-256 of the DER bytes. No algorithm negotiation, private-key import or event URL fetch is performed by the proposal service. The positive unit test independently encodes the flat event instead of using the product signing helper.

Typed pre/post identity, resource tenant, business state and revision must match real native marker evidence. The event principal/tenant/role must match the verified actor in both scans. The event must be bracketed by before completion and after start. Signature validity is displayed as authority UNCONFIRMED until explicit human trust review. Target timestamps/revision semantics remain trusted assertions, not independent clocks or causal witnesses. Canonically identical 0 and -0 are no change and therefore ABSTAIN, even if JavaScript Object.is distinguishes them. Wrong-key, tampered, unbracketed, incomplete, concurrent, reassigned, stale and contradictory evidence cannot create a proof matrix.

Before/after report hashes and proposal/review custody are revalidated at native admission. Historical result context is read from immutable records without rewriting an old outcome on later target drift. Key revocation is not an external automatic service; use explicit target-context invalidation or supersession/new review. There is no independent ownership oracle, issuer registry or self-signature-to-authority shortcut.
