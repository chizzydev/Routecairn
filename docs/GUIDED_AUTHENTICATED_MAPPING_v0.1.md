# Guided Authenticated Application Mapping v0.1

The existing Application Authorization Workbench now has a guided native observation and policy-binding journey. It uses the existing request-policy broker, scan workers, Adaptive observed inputs, inventory, SecurityCase IR, authorization synthesis, attack-state graph, contract compiler, finding evidence and real comparison services. No competing scanner or Trusted Discovery execution bridge is introduced.

## Operator journey

1. Register an OWNED LOCAL target with exact 127.0.0.1 origin and approved GET scope using existing target management. Create three target/org-bound saved disposable credentials with required principal, tenant and role verification. Open Application Authorization -> Start guided application mapping. Choose the target and each saved actor; inspect and confirm their saved metadata, which is not yet native verification.
2. Enter up to eight explicitly permitted GET URLs and declared route templates, selecting object or function reads and non-secret scalar JSON identity/tenant field paths. Confirm that those exact handlers are non-mutating: GET alone does not prove that. No crawling, URL expansion or response-derived executable URL is performed.
3. Review the durable observation revision, every exact baseline/identity/route request, actors, 40-request shared ceiling, 32 module checks, 8192-byte module response cap and concurrency one. Explicitly approve the observation within ten minutes. Preview itself transmits no target requests. Scope/DNS/credential/native custody checks remain authoritative. Route sends disable retries and redirects; the existing shared ledger bounds baseline/identity/runtime overhead.
4. Inspect native HTTP decisions, verified actor contexts, route templates and observed scalar marker fingerprints. Route/template semantics are declared seeds with response evidence, not automatically discovered truth. Raw response marker values, bodies and credentials are not retained in the new observation metadata. Selected scalar fingerprints distinguish strings from numbers.
5. Enter exact expected object/function and tenant values, policy rationale and each actor's ALLOW/DENY/UNKNOWN decision. Native marker types guide numeric binding without guessing values. Unknown policy stays unbound. An allowed control must have real successful native response and matching selected object/explicit tenant marker fingerprints. Missing controls or wrong-object/tenant bindings remain REQUIRES_BINDINGS. The resulting matrix is created by AuthorizationWorkbenchService using existing IR and guarded execution, with a separate explicit proof approval.
6. Execute the bounded reviewed matrix, inspect actual findings and uncertainty in existing views, then create a fresh review after the owned remediation and compare retained executions. A resolved finding is not an application-wide clean result. Source evidence, historical gates and unresolved near misses remain intact.

## Integrity and uncertainty

Schema 50 adds immutable observation revisions, one-use dispatch intents and acknowledgements. A separate mapping binding passes through the existing admission, queue and JOB_ACCEPTED checks before credentials or START_JOB. Shared ApplicationAuthorityBinding preserves the v0.1 target/credential checks and workbench context digest shape. Both simultaneous binding types are refused. An expired unconsumed review cannot dispatch. Previously acknowledged same-operator/digest commands return their recorded scan after expiry; consumed unacknowledged commands remain UNKNOWN, without replay or reauthorization.

Observation and workbench histories remain read-only. Failed/interrupted observations expose their safe failure summary and existing scan evidence. UNKNOWN offers no retry/reset/clearance. A changed form invalidates its observation preview and consent; late polling responses are ignored after effect cleanup. New approvals do not clear existing worker quarantine or recovery holds. Native report custody, registry hashes, exact check counts and completed execution are verified before using the map for policy binding. Foreign organizations, changed targets/credentials/plans and modified artifacts are refused. Distinct saved credential references must also represent distinct principal/tenant/role contexts; the actual identity endpoints still verify those contexts.

## Evidence and limits

The cumulative delivery contains genuine native SQLite/HTTP/Windows-worker RED/GREEN for post-expiry readback and duplicated actor-context acceptance, adversarial no-wire/UNKNOWN/concurrency/control/artifact checks, real Edge onboarding without pre-seeded observations or imported policy JSON, existing findings and two-resolved remediation comparison. The generated two-tenant app is self-maintained ground truth frozen before its first request. Secure and wrong-object-success cases are explicit controls; missing ALLOW response abstains. No independent detection precision/recall or field/provider acceptance is claimed.

This is source-mode Windows development acceptance. Existing target/vault registration is a prerequisite; account creation and a general project setup wizard are not automated. Explicit route seeds are still entered by the operator. Broad authenticated crawling, OpenAPI/schema ingestion, automatic role/ownership discovery, mutating workflows, team/provider/production/release and full-suite acceptance remain separate backlog work. Three saved actors plus anonymous and selected REST GET routes are the supported slice. Numeric marker binding has focused UI/contract coverage; the native fixture uses string IDs.

All existing operational HOLDs remain, including Stage D D1-D4, Trusted Discovery execution OFF, A1B/real609 materialization and release packaging. A1C remains ZERO-COMMIT and Ubuntu remains paused. No external target scanning, dependency installation, release build/pack/publish, Git history/index mutation or retained-evidence deletion is performed by this increment.
