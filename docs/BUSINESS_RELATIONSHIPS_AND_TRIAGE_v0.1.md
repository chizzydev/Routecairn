# Reviewed Multi-Step Business-Flow Relationships & Evidence-Centered Operator Triage v0.1

## What the product does

Use the existing Application Authorization workspace. Set up an owned local application with three distinct disposable actor contracts, then explicitly review and authorize exact GET observations. Start from existing schema/discovery/manual mapping; this increment grants no crawling or mutation authority.

Under evidence-grounded hypotheses, draft an ordered flow, then connect named producer and consumer operations. Select an already observed producer identifier, consumer reference and separate version field for each entity. Tenant fields are mandatory. The producer identifier must be the mapped entity identity, never a tenant label. The consumer reference may be a declared state observation; no new response fields are silently read. Maximum four ordered operations, three forward relationships, eight mapped routes, two state fields per route, four actor contexts. Duplicate, reversed, self, unknown-route and secret-field declarations are refused.

The relationship projection verifies exact native actor/credential slots, verified principal/tenant/role, request and response check attribution, typed fingerprints, primary positive control and per-entity versions. A numeric identifier does not equal a string identifier. Actor-specific different objects, stale versions and resource tenant changes are counterevidence. Matching HTTP200, route names, advertised schemas, sequence order and response similarity are never ownership or authorization truth. The native report hash, scan ID, map/context binding, actor fingerprint and check IDs stay attached.

Read operations are called producers/consumers only in the sense of observed entity references. Reads are not a transactional application snapshot. Matching references and declared prerequisites are not proof of causality, legitimate state changes, a write-to-read exploit or a successfully exploited business transition.

Cross-step questions rank actual matching references across actor/tenant contexts with deterministic priorities, never calibrated likelihood. Missing controls abstain. Review every non-secret object/tenant/state value, every actor decision and the owner-supplied business-policy explanation in the existing differential review. Full-flow approval is required for a relationship proposal; single-endpoint review cannot launder an unreviewed relationship into proof. No request is sent by proposal generation or policy review.

The existing workbench compiles the exact role/object/state contracts and prerequisite checks through the existing IR/planner. Explicit separate approval, fresh immutable target/scope/credential/plan binding, one-use review decisions, bounded native Windows workers, max40 shared requests, max32 module requests, concurrency1 and existing cleanup/quarantine rules remain. Known positive controls are required; wrong-object200, stale state and incomplete responses cannot become findings. Native proof and comparisons are the existing engines, not a parallel scanner.

## Analyst journey

The witness view distinguishes native observations, owner declarations, absent controls and untested questions. The linked evidence triage appears both in hypothesis review and directly beside a workbench execution. Refresh is read-only and sends no target request. Inspect exact scan IDs, response hashes, actor/check fingerprints, native outcomes, findings, comparison coverage and existing observed-state/assurance history.

An analyst may append an immutable, evidence-digest-bound note: investigate, request owner context or record owner-expected behavior. CSRF, scan/credential permissions, selected organization and resource-use checks are server enforced. Notes cannot suppress findings, declare resolution, clear UNKNOWN/quarantine, replay a dispatch or grant execution. A lost acknowledgement is unconfirmed; inspect history before another explicit action. There is no automatic retry or rollback claim.

The projection uses a consistent SQLite read transaction. Its bounded views show newest proofs/notes and disclose incomplete history; truncated views cannot quietly hide a later UNKNOWN. Failed, partial, invalid, incomparable or incomplete comparison evidence requires review. Historical findings remain visible after a complete comparison records an exact remediation delta. Never infer full application security from a PASS in the reviewed read-only checks.

Existing Observed-State Regression policies and assessments are shown through their own integrity-checked service. No linked policy means assurance is NOT TESTED. Business-reference evidence does not supply a signed transition/event authority, create a regression policy or authorize Continuous Assurance. Use the existing separate trusted-event policy workflow. Mutation, transition authorization and causal proof remain untested/HOLD.

## Runtime evidence and scope

Two deliberately different owned implementations exercise the reusable production contracts: a Node append-only event-log projection for fulfilment and a separately implemented Python relational SQLite episode/claim service. The shared harness only supplies dashboard orchestration and credential/wire recording; domain reads execute separately. The Python process is attached to native custody before its START command permits a listener. Its normal owned SQLite files and native custody receipts are retained. Fixture-only remediation changes are not target HTTP mutations or deployment fixes.

Positive and negative scenarios include vulnerable linked access, correct denial across tenant/role contexts, legitimate sharing, wrong-object200, stale versions, missing primary control, missing references and numeric/string disagreement. Predictions are saved from actual native outcomes before accuracy assertions; a failure before a prediction remains an explicit UNTESTED fixed case. No test is dropped from the denominator.

These are Codex-authored, known-label fixtures. Different technology/domain implementations are useful diversity controls, not independent authorship or broad real-world validity. Production APIs/UI now accept reusable owner-declared relationships for arbitrary admitted owned loopback mappings. Runtime acceptance still has not been demonstrated on a non-fixture owner application. No independent or blinded accuracy claim is made.
