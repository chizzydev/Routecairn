## Prepare the real exercise

Copy `examples/external-acceptance.example.json` into a private working directory. It remains a template and is deliberately blocked from independent execution until replaced. Prepare all eight genuine target lanes, disposable accounts and positive/negative assertions. Obtain target-owner authorization for the exact actions and cleanup grace period. Do not use real payment credentials or real transactions.

```powershell
routecairn external-acceptance prepare --manifest approved-manifest.json --release-artifact routecairn.tgz --bindings approved-bindings.json --trust operator-trust.json --output readiness.json
```

Readiness sends no HTTP/provider requests. `--resolve-dns` optionally verifies DNS addresses; the actual runner always does this preflight before transmitting. A missing input, placeholder, missing credential variable, untrusted key, changed artifact, loopback target or shallow subscription contract produces `BLOCKED` and exit code 2. `READY` is only preparation status; it is not an acceptance pass.

### File bindings

The bindings file conforms to `externalAcceptanceBindingsSchema`:

```json
{
  "schemaVersion": 1,
  "authorizationProof": { "path": "owner-approval.pdf", "sha256": "<actual 64-character SHA-256>" },
  "lanes": [
    {
      "id": "<manifest lane id>",
      "reproduction": { "path": "procedure.md", "sha256": "<actual SHA-256>" },
      "deployment": { "path": "deployment-evidence.json", "sha256": "<actual SHA-256>" }
    }
  ]
}
```

Supply exactly eight distinct lane records. Each reproduction digest must match the lane's `reproductionSha256`; each deployment file digest must match `targetFingerprint`. The authorization file digest must match `authorization.proofSha256`. Paths resolve against the CLI working directory. Approval and reproduction files are hashed, never automatically downloaded or executed. The owner/operator must establish that deployment evidence identifies the actual target revision; a file hash alone cannot do so.

### Independent operator trust

Obtain the operator's public key outside the evidence bundle. A separately administered registry conforms to `externalAcceptanceTrustSchema`, with `schemaVersion: 1` and an `operators` array. Each operator has:

- `keyId`: SHA-256 of the Ed25519 SPKI DER public key.
- `organization`, `publicKeyPem`, `validFrom`, `validUntil`, `revoked`.
- `independentlyVetted: true` and a real `vettingReference`.

The administrator establishes the organization's independence before registration. A boolean declaration or a key generated by the RouteCairn author does not establish independence. Invalid key material, mismatched key IDs, duplicate keys, invalid intervals, expiry and revocation fail verification. The applicable operator entry is committed into the signed evidence. Adding unrelated operators does not invalidate a bundle; changing the applicable entry requires renewed review.

## Native GraphQL subscriptions

An HTTP response labeled as a subscription is insufficient for independent readiness. Subscription actions must declare `request.transport`:

- **WebSocket:** `{ "kind": "GRAPHQL_WS", "protocol": "graphql-transport-ws", "document": "subscription { ... }", "variables": {}, "connectionPayload": { ... }, "maxMessages": 10 }`. Use HTTP(S) origin aliases and method GET; the runner opens WS(S), waits for `connection_ack`, then subscribes. Owner success requires negotiated protocol and a data message. Foreign denial requires a rejection or error message and no data. Response assertions see `{ "protocol": "...", "messages": [...] }`, with status 101 for an accepted upgrade.
- **SSE:** `{ "kind": "GRAPHQL_SSE", "maxEvents": 1 }`, method GET or POST and a provider-specific GraphQL request body/path. Owner success requires an event-stream response containing data. Foreign denial must contain no data and must produce an error or denied status. Assertions see `{ "events": [...] }`.

Both transports are DNS-pinned, origin-scoped and bounded by the action timeout, authorization expiry, request-byte limit, response-byte limit and message/event count. Only response fingerprints and status codes are retained. Browser-mediated MFA/passkey and payment/provider adapters still require an independently maintained reproduction procedure and authentic provider execution; naming an adapter action never proves these behaviors by itself.

## Run and verify

```powershell
routecairn external-acceptance run --manifest approved-manifest.json --release-artifact routecairn.tgz --bindings approved-bindings.json --trust operator-trust.json --signing-key-env INDEPENDENT_OPERATOR_SIGNING_KEY --output private-evidence
routecairn external-acceptance verify --bundle <run-directory>/external-acceptance-bundle.json --manifest <run-directory>/external-acceptance-manifest.json --release-artifact routecairn.tgz --trusted-public-key independently-obtained-operator.pem --bindings approved-bindings.json --trust operator-trust.json
```

Credential values and private keys are read from the declared environment, not from checked-in manifests. Authorization/cookie/key/password/token fields must use secret/capture references. Capture references must be declared before consumption; path values are encoded to prevent captured identifiers from changing the route. Request body size, execution duration and cleanup grace are bounded. Cleanup continues after a primary failure within the owner-authorized grace period, with failures preserved in evidence.

The release tarball is validated and committed by digest. Its metadata must match the running package version. This binds an operator's release declaration to artifact bytes; it is not remote runtime attestation of every executed module. Preserve build provenance and independent runner logs for stronger execution identity.

Verification checks DSSE type, Ed25519 key, the complete signed predicate, manifest/release commitments, unique action identities, response-status contracts, semantic consistency, cleanup and authorization timing. A valid signature alone is reported as `verified: true`; a genuine passing independent exercise additionally requires `independentAcceptanceVerified: true`. Failed quality results exit with code 2.

`run --fixture` is explicitly limited to loopback. Its provenance remains `FIXTURE`, `externalTargetsTested: false`, `independentlyTrustedOperator: false`. `verify --allow-fixture` accepts its engineering signature while keeping `independentAcceptanceVerified: false`. Legacy bundles without provenance likewise cannot establish independent acceptance.

## Fresh disposable Decide exercise

`exercise-decide` creates two new accounts administratively using the owner's explicitly named `decide-api` checkout and database credentials. It tests the deployed custom API's account identity, unauthenticated denial, foreign-session revocation denial, profile identity binding, refresh rotation/replay, logout and account deletion. Its authorization contract must explicitly permit these operations, name the HTTPS API origin, limit requests/accounts and define the execution and cleanup windows. `ownedDecideAuthorizationSchema` is the executable contract.

```powershell
routecairn external-acceptance exercise-decide --authorization owner-authorization.json --decide-api-directory C:/Users/HP/decide-api --database-ca /private/supabase-root.crt --output .routecairn-external-acceptance/owned-decide
```

The backend checkout must supply its installed `bcrypt` and `dotenv` dependencies; RouteCairn supplies `pg`. Only the `DATABASE_URL` credential is consumed from the named environment file (defaults to the backend's `.env`). Verified TLS and a CA file are mandatory; conflicting connection-string SSL settings are rejected. Credentials stay in memory. Generated `.invalid` email addresses receive no messages: email ownership is administratively verified, so this does **not** test registration/email delivery or MFA/passkeys.

The exact generated UUID/email identities are saved to `private-recovery.json` before insertion; no passwords or tokens are saved. Provisioning is transactional. After success or failure, cleanup uses the accounts' own authenticated endpoints and then a mandatory exact-identity database cleanup/check. A journal that remains `CLEANUP_REQUIRED` must be recovered:

```powershell
routecairn external-acceptance recover-decide --recovery <run-directory>/private-recovery.json --decide-api-directory C:/Users/HP/decide-api --database-ca /private/supabase-root.crt
```

Keep recovery journals private and inside ignored working directories. Recovery refuses unrelated names, duplicate identities and mismatched run namespaces. Evidence retains only case results, response fingerprints, hashed actor identities and cleanup state. Failure messages never include raw provider/database errors or credentials. Retain the portable `owned-decide-exercise.json` and checksum after reviewing them; never copy the private recovery journal into a public evidence directory.

The actual fresh 2026-09-30 run is retained in `acceptance/decide/2026-09-30/fresh-owned-exercise.json`: two accounts, 20 HTTP requests, 18 passing cases, two failing refresh rotation/replay contracts, and verified removal of both accounts and their sessions. This remains owner-operated partial evidence. Supabase hosts the Decide database, but database access does not establish hosted management access, Storage/RPC acceptance or the eight-lane grid. A locally corrected backend is not a deployed remediation pass.

## Hosted Supabase disposable exercise

`exercise-supabase` now provisions and actually exercises the hosted Supabase service with two fresh Auth identities, a generated RLS table, a security-invoker RPC, and a private bucket containing a small text proof. It requires a currently valid explicit owner authorization, the existing project publishable/secret keys in an ignored private file, and verified TLS database access bound to the same Supabase project. It never changes an existing application table, function, policy or bucket. A dedicated generated policy on `storage.objects` applies only to the run's exact bucket.

```powershell
routecairn external-acceptance exercise-supabase --authorization owner-supabase-authorization.json --credentials /private/provider-private.json --decide-api-directory C:/Users/HP/decide-api --database-ca /private/supabase-root.crt --output .routecairn-external-acceptance/supabase
routecairn external-acceptance recover-supabase --authorization owner-supabase-authorization.json --credentials /private/provider-private.json --decide-api-directory C:/Users/HP/decide-api --database-ca /private/supabase-root.crt --recovery <run-directory>/private-recovery.json
```

The private credentials schema has `projectRef`, `publishableKey`, `secretKey`; it supports Supabase's current `sb_publishable_` and `sb_secret_` keys. Do not commit this file or expose the secret key in browser clients. The strict authorization schema is exported as `ownedSupabaseAuthorizationSchema`: version, exact project reference, authorizing owner/reference, start/expiry, 40–60 requests, 0.1–2 requests/second, exactly two accounts, explicit isolated-resource provisioning and deletion permissions, and a bounded cleanup grace.

The checks require positive owner responses as well as foreign/anonymous denial. Table checks also prove a foreign update did not change the owner's data. Storage checks cover authenticated owner read, foreign read, anonymous/private-public path denial, foreign overwrite, and unchanged owner content. RPC checks prove the same exact object is returned to its owner and invisible to the other identity.

Provisioning never sends verification email: Auth administrator creation explicitly confirms only the generated disposable addresses. A private journal containing the generated run/project identities is saved before mutations. Ambiguous user-creation responses are recovered by exact generated emails; cleanup enumerates only the generated bucket's bounded UUID/proof paths. Object deletion is synchronous through the Storage API before deleting the bucket. Do not delete `storage.objects` rows directly: that does not remove the provider's underlying files. Database cleanup precedes Auth deletion to remove acceptance foreign keys. Absence verification checks accounts, bucket, objects, policy, table and RPC.

PostgREST schema propagation is observed with at most three scoped read-only readiness requests. Recognized `PGRST205` propagation responses remain `PENDING` observations in the evidence; they are never relabeled as successful ownership checks. Readiness exhaustion fails the exercise and still triggers cleanup. Eight HTTP requests are reserved for cleanup, and both execution and recovery obey authorization expiry/grace. Provider error contents, account IDs/emails, passwords and tokens are excluded from portable receipts.

The actual 2026-09-30 hosted run is retained under `acceptance/supabase/2026-09-30`: 27 HTTP requests, 26 passed receipts, one schema-cache propagation observation, and verified zero remaining resources. The initial failed run and its separate verified recovery record are also retained. These are **owner-created fixtures on an actual hosted provider**. They establish operational hosted RLS/Storage/RPC testing; they do not establish independently maintained acceptance, existing Decide application policy correctness, OIDC/MFA/passkeys, payment processing, or the complete eight-lane grid.
