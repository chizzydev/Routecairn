# Evidence-grounded Security Hypotheses v0.1

## Product flow

In existing Application Authorization > guided mapping, open a saved map and Evidence-grounded security hypotheses. Generate a proposal without application traffic. Inspect ranked, deduplicated route questions, successful primary control, other actors' access/denial/wrong-object evidence, exact native check/IR/source references and typed non-secret marker fingerprints. Select a candidate; explicitly declare ownership, expected typed identifiers and policy. This records one immutable decision and builds the existing Workbench matrix. Review its exact requests and separately authorize native proof. Findings, remediation retest and finding comparison use the existing surfaces. Generation, scores and map differences never create findings or confer execution.

The initial rule asks whether matching typed object/tenant markers appear for other verified actors. It does not know that access is forbidden: legitimate shared resources can produce the same question. The owner may reject expected sharing or permit authenticated actors in a reviewed policy; real proof then produces no finding. All-actor wrong-object responses can also produce a question until owner-declared values reject the mismatch. Wrong-object responses differing from a successful primary control abstain. Missing control/identity/IR, incomplete observations or conflicting duplicate observations abstain. Partial or corrupt reports refuse generation. No quiet green counters are inferred.

## Review and continuity

SQLite migration52 adds immutable proposals and one decision per proposal/candidate. Human ownership/policy confirmations are mandatory for review. Rejection is terminal for that proposal; a new explicitly superseding proposal may record a different review, and invalidates old linked matrices at preview/admission/native JOB_ACCEPTED. Creating unrelated proposals/maps never implicitly supersedes another context. A comparison or score cannot clear worker quarantine or replay a scan.

Changing scope, credential context, target, source bytes, algorithm, markers or policy invalidates the reviewed proof binding. The existing Workbench input carries a hypothesisReviewId. The existing service, queue, exact plan and native boundary revalidate it; there is no new execution endpoint. Reviews belong to their operator when creating linked matrices. Ordinary existing matrix dispatch approval still applies. After an asynchronous ordinary preview, source and supersession are rechecked before recording.

Decision and subsequent matrix creation are separate, non-transmitting persistence steps. If matrix persistence/acknowledgement fails, the append-only review remains visible with no linked matrix. Retrying the same decision is refused; no scan/replay/reset is offered. Review history links existing matrices for inspection, with a separate native dispatch approval. Existing uncertain dispatches remain UNKNOWN.

All proposal reads require existing scans.read, credentials.readSummary and organization read authority; generation/review additionally require scans.create, credentials.use and selected target/credential resources.use plus ordinary CSRF checks. VIEWER retains existing permitted scan evidence, cannot read restricted actor summaries or mutate hypotheses.
